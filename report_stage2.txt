1) FAULT DETECTION MECHANISM
   The system uses heartbeats to detect worker failures. Every worker sends a small “I’m alive” message (HEARTBEAT tag) to the master after reading every 1000 lines while it is processing a log file. 
   The master records the last time it heard from each worker in last_heartbeat[rank]. A background check compares the current time to each stored timestamp.
   If a worker has been silent for > 4 seconds (HEARTBEAT_TIMEOUT), the master concludes that the worker has crashed or become unreachable. The master then informs the user/client that the worker has failed and then
   initiates reassignment of the work.

2) RECOVERY STRATEGY
   Each worker’s current file is tracked in assigned[rank]. On failure detection, the master retrieves that filename, removes it from assigned, re-inserts it at the front of pending (it's a list which behaves as a stack),
   The next worker that requests work automatically receives this file. The failed worker’s rank is added to failed_workers for reporting.

3) CHECKPOINTING DESIGN
   After every 5 files are processed by the workers, or at a normal termination, the master saves a checkpoint in checkpoint.json. Each checkpoint consists of - timestamp, counts(of the different tages like WARN etc.),
   the number of processed files, pending files and failed workers.

5) CONSISTENCY MODEL FOLLOWED
   The system follows eventual consistency. Each worker sends partial results immediately after finishing a file. The master merges those counts as soon as they arrive.
   The trade-offs here are that the worker nodes wouldnt have to wait for the other workers to gain the same state of completion. This would lead to lower latency and hence faster result generation. It is ideal for 
   our distributed system because we are not focused on the accuracy of our results right now but rather on increasing efficiency of the system.
   Hence, Eventual consistency led to better throughput, and less coordination overhead.
6) DESIGN DECISIONS
   I dont know about interesting, but I found the decisions appropriate for this assignment.
   Instead of time-based heartbeat generation, I have used a callback type heartbeat generation, because the former was complex to implement as it needed a new thread for timer-based heartbeat sending. 
   I think the use of a stack data structure for assigning the pending files was a very interesting choice as it followed FIFO, and hence makes very easy to assign the files to workers, and also ensures fair distribution.

7) (ADDITIONAL - CHALLENGES FACED)
   Early versions of code used blocking assignment everywhere and hence runtimes were very large. Changed probe() to Iprobe(), i.e., non-blocking assignment.
   Restarting without filtering already processed files caused duplicates. Added processed_files set and skip logic when rebuilding pending queue.
   The loop "while assigned or pending" is necessary, but it led to last 2-3 files not being read because the workers complete their work, send work_result and      hence are removed from assigned, but they also send work_request, but pending is already empty and the no_more_work is sent to the workers, and hence loop        fails and few files were left unread. An additional drain phase was added for this. 
8) LIMITATIONS
   Does not have any solution if the master itself fails. Re-election of new master will not happen and the program will just stop.
