4)Work Distribution Strategy  - 
  The work distribution in the parallel log analyser follows a static round-robin strategy.
  The master process first collects the list of all available .log files and distributes them evenly among all participating MPI processes.
  This is implemented using the expression chunks[i % num_procs], which assigns each file to a process in cyclic order.
  Consequently, every process receives approximately the same number of files, even if the file sizes vary.
  This approach ensures a balanced workload with the overhead of static scheduling, which is appropriate for the Stage 1 static analysis requirement.

5)Challenges faced 
  1 - I earlier tried using the reduce() and MPI.SUM function to sum the individual dictionaries of counts of each level of each worker directly, but later learned that it cannot directly be used for 
      adding dictionaries in that manner. So I learned that I would have to create a list and then loop through it to add the dictionaries and store the counts in a new dictionary. 
  2 - Running the base_log_analyser gives different runtimes each time it is run. So my earlier approach of just running it once and taking that runtime as a static runtime for sequential analysis was
      innacurate. Hence, as a solution I applied a method called sub process in the parallel_log_analyser itself that runs the base_log_analyser file each time the former is run, so that both times are calculated 
      simultaneously and the corresponding speedup. This was considered better because the conditions (of CPU scheduling) will be the same for both so both the times will be nearly equally affected. There is still
      a problem of one operation filling the cache for the other to run faster. But of all other methods, I found this one to be more feasible and quick.
  3 - I faced the problem of there not being enough cores on my CPU to make 8 individual workers for the last case, and hence I made the process partially sequential using --oversubscribe which basically 
      does time-sharing of the CPU storage between workers.
6)Observations about scalability - Adding more CPU cores as workers gives a better runtime. So scalacility is limited only by the number of cores that are available. So it is greatly scalable, just get a CPU
                                   with more cores and efficiency increases.
